### Category B: 3 New Cross-Sheet Invariants (FE-1..FE-3)

#### FE-1: F-24 — `.mcp.json` ↔ `mcp-tool-registry.json` Servers Key Sync

| Attribute | Detail |
|-----------|--------|
| Rule | `.mcp.json` mcpServers keys MUST equal `mcp-tool-registry.json` servers keys (sets comparison; ScraplingServer↔scrapling case-fold per D-SF-02 alignment) |
| Severity | HIGH → RED verdict |
| Category | engine_consistency |
| Detection | `check_F_24` reads both files; normalizes ScraplingServer→scrapling; emits FAIL on set delta |
| Trigger | Engine repo state; runs on every drift-check invocation |
| FAIL cases | Server in .mcp.json but not registry (orphan transport) OR server in registry but not .mcp.json (orphan inventory) |
| SKIP cases | Either file missing (engine state ambiguous) |
| Test cases (3+) | (1) Match: both have {gsc, dataforseo, scrapling, sf} → PASS; (2) Orphan transport: .mcp.json has +newserver missing from registry → FAIL; (3) Orphan inventory: registry has +legacy missing from .mcp.json → FAIL |
| Lines of code | ~80L check_F_24 function + 3+ test cases ~60L |

#### FE-2: F-25 — `sf.mcp.enabled` Requires `schema_version` ≥1.5

| Attribute | Detail |
|-----------|--------|
| Rule | If `project.config.sf.mcp.enabled=true`, `project.config.schema_version` MUST be ≥"1.5" (Migration 0005 prerequisite) |
| Severity | HIGH → RED verdict |
| Category | csr_mcp (consistency check for SF MCP) |
| Detection | `check_F_25` reads project.config.json; if sf.mcp.enabled=true + schema_version<1.5 → FAIL |
| Trigger | Per-project drift-check |
| FAIL cases | enabled=true + schema_version="1.4" (or lower) — impossible per Migration 0005 lock but defensive check |
| PASS cases | (a) enabled=false (any schema_version); (b) enabled=true + schema_version≥1.5; (c) sf block absent (default behavior) |
| SKIP cases | project.config.json missing OR schema_version field absent (legacy state) |
| Test cases (4+) | (1) enabled=true + schema_version=1.5 → PASS; (2) enabled=true + schema_version=1.4 → FAIL; (3) enabled=false + schema_version=1.4 → PASS; (4) sf block absent → PASS |
| Lines of code | ~70L check_F_25 function + 4+ test cases ~80L |

#### FE-3: F-26 — Orphan SF GUI Crawl Detection (AMBER)

| Attribute | Detail |
|-----------|--------|
| Rule | If `_state/workflows/{run_id}.json` shows sf-crawl-orchestrator in status="paused" or "failed" AND `mcp__sf__sf_crawl_progress({crawl_id})` returns IN_PROGRESS, surface AMBER warning |
| Severity | MEDIUM → AMBER verdict (NOT RED) |
| Category | csr_mcp + mcp_runtime |
| Detection | `check_F_26` reads workflow JSONs; for each paused/failed sf-crawl-orchestrator run, optionally call SF MCP `/sf_crawl_progress` (only if MCP responding within 1s health probe) |
| Trigger | Per-project drift-check (operator-level cleanup hint, not blocking) |
| AMBER cases | Workflow paused/failed + SF GUI shows crawl IN_PROGRESS (orphan: workflow state + GUI state disagree) |
| PASS cases | (a) No paused/failed sf-crawl-orchestrator runs; (b) All paused/failed runs have NO matching IN_PROGRESS SF GUI crawl |
| SKIP cases | SF MCP unreachable (health probe FAIL within 1s; avoid blocking drift-check on MCP downtime) |
| Test cases (4+) | (1) No orphan: workflow done + GUI clean → PASS; (2) Orphan: workflow failed + GUI IN_PROGRESS → AMBER; (3) MCP down: workflow paused + MCP unreachable → SKIP; (4) Multiple orphans: 2 paused + 2 GUI IN_PROGRESS → AMBER with details |
| Lines of code | ~120L check_F_26 function (MCP HTTP call via sf_mcp_client) + 4+ test cases ~100L |

## Multi-Session Execution Model (D-V1.9-08 — v1.8 paterni reuse)

Per `docs/SESSION_PROTOCOL.md` §13.1-13.4 + v1.8 multi-session execution model (D-SF-17), v1.9 reuses the same Manager+Worker pattern:

### Manager Session — Decision-Maker Role

- Holds spec + plan in context (v1.9 = ~700 lines spec + 600 lines worker prompts + 200 lines manager bootstrap; fits comfortably in 200K window)
- Generates Worker Prompts from companion file (`docs/superpowers/plans/2026-05-26-v1.9-worker-prompts.md`)
- Processes Worker Output Packages (compact return per `SESSION_PROTOCOL.md` §13.4 format)
- Updates `docs/PHASE_STATUS.md`, `docs/DECISIONS.md`, `docs/OPEN_QUESTIONS.md`, `docs/CONTEXT_LEDGER.md` between phases
- Makes phase gateway decisions (GO/NO-GO to next phase)
- Resolves Q-V1.9-* open questions as they surface

**Manager does NOT (forbidden actions reused from v1.8):**
- Read full worker transcripts (only Worker Output Packages)
- Touch implementation files directly (delegates to Workers)
- Edit spec or worker prompts files mid-execution (notes deviations for v2.4 retro)
- Push git tag to remote without explicit operator approval
- Skip a phase
- Run pytest themselves (Workers report)

### Worker Sessions — Fresh per Phase

One fresh Worker Session per Phase (7 total). Each Worker:

1. Receives self-contained prompt from companion file (Prompt 1..7)
2. Bootstraps via `SESSION_PROTOCOL.md` §13.2 fresh wakeup (<15KB initial load)
3. Reads ONLY files listed in prompt
4. Executes phase tasks in order
5. Runs verification commands (explicit pytest/bash command per task)
6. Returns Worker Output Package to Manager
7. Session ends — no carryover

**Phase ordering enforces serial execution.** Phase 2 cannot start until Phase 1 Worker returns Output Package and Manager confirms GO.

### Worker Output Package Format (per SESSION_PROTOCOL.md §13.4)

Reuse v1.8 format exactly. Compact (~1-2KB) return: Files Created/Modified + Decisions Made + Open Questions Surfaced + Next Step Recommended + Verification.

### Coordination Channel — git + workflow_runner state

Same as v1.8 — between Workers, state lives in: `git log` + `docs/PHASE_STATUS.md` + `_state/workflows/{run_id}.json` + `tests/` GREEN status.
